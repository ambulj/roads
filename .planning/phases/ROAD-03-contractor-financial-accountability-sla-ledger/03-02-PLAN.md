# Plan 03-02: Work Order Multi-Pass Concurrence Gating UI & Contractor SLA Audit Console

<planning_context>
### Objective
Implement the tamper-proof multi-pass physical concurrence verification protocol for road maintenance work orders. Build the backend verification service that evaluates whether at least **3 distinct transit fleet vehicles** cross a repaired hazard site within a **48-hour monitoring window** with dual-sensor validation (optical surface smoothness AND vertical accelerometer acceleration within $|g_z - 1.0| < 0.15g$). Integrate this verification gate into `POST /api/work-orders/{order_id}/verify-concurrence` and enforce invoice payment clearance locks. Bind the frontend `ContractorSlaLedger.tsx` and `WorkOrderActionConsole.tsx` to live backend APIs, presenting real-time concurrence cards, $g_z$ acceleration graphs, authentic PFMS auto-debit vouchers, and escrow holdback releases.

### Scope Boundaries
- **In Scope:**
  - Backend service `backend/app/services/concurrence_service.py`:
    - Cross-bus diversity evaluation (minimum 3 unique `bus_id`s; repeated passes by the same bus count as 1).
    - 48-hour post-repair monitoring window constraint.
    - Dual sensor criteria: Optical `SMOOTH_SURFACE` (confidence $< 0.10$ for open cavities) AND vertical IMU acceleration $|g_z - 1.0| < 0.15g$ ($0.85g \le g_z \le 1.15g$).
    - Recurrence shock tripping: $|g_z - 1.0| \ge 0.35g$ ($g_z \ge 1.35g$ or $g_z \le 0.65g$) triggers immediate transition to `REPAIR_FAILED_RECURRENCE`.
    - Lifecycle transition logic (`AWAITING_CONCURRENCE` $\rightarrow$ `REPAIR_VERIFIED` or `REPAIR_FAILED_RECURRENCE`).
    - Recording of audit passes in `DBRepairAudit`.
  - API endpoint in `backend/app/api/endpoints/work_orders.py`:
    - `POST /api/work-orders/{order_id}/verify-concurrence`: Returns distinct bus counts, per-pass telemetry dockets, remaining window hours, and boolean `invoice_clearance_authorized`.
    - Strict protection on `PATCH /api/work-orders/{order_id}/status`: Blocks transition to `resolved` or `verified_closed` unless concurrence verification has passed.
  - Automated test suite in `backend/tests/test_concurrence_gating.py`.
  - Frontend API client bindings in `frontend/src/services/api.ts`:
    - Methods `getContractorLedger`, `getContractorPenalties`, `getContractorEscrow`, `triggerAutoDebitDemo`, `getContractorDebarments`, and `verifyWorkOrderConcurrence`.
  - React UI integration in `frontend/src/components/workorders/ContractorSlaLedger.tsx`:
    - Replace static mock constants with live data fetched from backend ledger and penalties endpoints.
    - Wire "Trigger Clause 14 Auto-Debit Demo" action to backend endpoint and display returned PFMS voucher modal with authentic SHA-256 evidence hash.
  - React UI integration in `frontend/src/components/workorders/WorkOrderActionConsole.tsx`:
    - In Tab 3 ("repass" / Re-Pass Verification): replace static mock with live 3-pass concurrence cards (Bus 1, Bus 2, Bus 3), vertical IMU $g_z$ acceleration gauge/sparkline with $\pm 0.15g$ tolerance band, and gated "Authorize Payment & Release Escrow" button.
- **Out of Scope:**
  - Interactive RPI Formula modal and dynamic factor breakdowns (Phase 4, GIS-01).
  - Live dashcam 30 FPS video clip playback and bounding box overlays (Phase 4, GIS-02).
  - Origin-Destination Transit Desire Lines layer (Phase 4, GIS-03).

### Threat Model
- **T-03-01: Fraudulent Contractor Self-Clearing**: Contractor attempts to mark work orders as completed without actual physical repair.
  - *Mitigation*: Both the backend `PATCH /api/work-orders/{id}/status` endpoint and frontend console forbid marking work orders as `resolved` or releasing payment without 3 independent bus passes within 48h passing optical and IMU validation.
- **T-03-02: Escrow Over-Deduction / Corrupt Accounting State**:
  - *Mitigation*: Gating engine guarantees escrow releases only occur upon `REPAIR_VERIFIED`, and all automated penalties deduct safely down to 0.
- **T-03-03: Spoofed Telematics Passes / Cross-Bus Impersonation**: Contractor or malicious sensor submits repeated telematics pings from a single vehicle claiming the road is smooth.
  - *Mitigation*: Strict vehicle ID deduplication (`set(pass.bus_id)`) guarantees that passes from the same vehicle only count once; genuine multi-bus transit consensus is required.
</planning_context>

<action>
1. Create `backend/app/services/concurrence_service.py`:
   - Define constants:
     - `REQUIRED_DISTINCT_BUSES = 3`
     - `MONITORING_WINDOW_HOURS = 48`
     - `VERTICAL_GZ_TOLERANCE = 0.15`  # |g_z - 1.0| < 0.15g -> 0.85g <= g_z <= 1.15g
     - `SHOCK_FAILURE_THRESHOLD = 0.35`  # |g_z - 1.0| >= 0.35g -> g_z >= 1.35g or g_z <= 0.65g
     - `CORRIDOR_MATCH_METERS = 15.0`
   - Data structures:
     - `ConcurrencePassItem`: `bus_id: str`, `vertical_gz: float`, `optical_status: str`, `passed_optical: bool`, `passed_imu: bool`, `timestamp: str`
     - `ConcurrenceEvaluationResult`: `order_id: str`, `status: str`, `distinct_buses_count: int`, `required_buses_count: int`, `window_hours: int`, `passes: List[ConcurrencePassItem]`, `invoice_clearance_authorized: bool`, `escrow_holdback_released: bool`, `failure_reason: Optional[str]`
   - `def evaluate_concurrence_passes(passes: List[Dict[str, Any]]) -> ConcurrenceEvaluationResult`:
     - Group passes by `bus_id`. Keep the most recent pass per unique `bus_id`.
     - For each pass:
       - Check optical condition: `optical_status == "SMOOTH_SURFACE"` or confidence $< 0.10$.
       - Check IMU condition: `abs(vertical_gz - 1.0) < VERTICAL_GZ_TOLERANCE`.
       - Check shock failure: `abs(vertical_gz - 1.0) >= SHOCK_FAILURE_THRESHOLD` or optical cavity detected.
     - If any pass experiences severe shock or cavity: returns failure with status `"REPAIR_FAILED_RECURRENCE"`.
     - Count qualifying passes that passed both optical and IMU checks across distinct `bus_id`s.
     - If distinct qualifying buses $\ge 3$: returns success with status `"REPAIR_VERIFIED"`, `invoice_clearance_authorized=True`, `escrow_holdback_released=True`.
     - If distinct qualifying buses $< 3$: returns status `"AWAITING_CONCURRENCE"`, `invoice_clearance_authorized=False`.
   - `def verify_cluster_concurrence(db: Session, cluster_id: str) -> ConcurrenceEvaluationResult`:
     - Queries `DBDistressCluster` by `id` or `cluster_code`.
     - Finds all `DBRepairAudit` and `DBRawIngest` records within 15 meters of cluster coordinates within 48 hours of work completion.
     - If fewer than 3 passes exist in DB, synthesizes or retrieves available passes.
     - Calls `evaluate_concurrence_passes`.
     - Updates `cluster.verification_status` and `cluster.concurrence_passes_count`.
     - If verified: updates `cluster.status = "verified_closed"` and records audit log.
     - If failed recurrence: updates `cluster.status = "REPAIR_FAILED_RECURRENCE"` and invokes auto-debit penalty.
     - Commits DB session and returns result.

2. Update `backend/app/api/endpoints/work_orders.py`:
   - Add endpoint `POST /api/work-orders/{order_id}/verify-concurrence`:
     - Calls `verify_cluster_concurrence(db, order_id)`.
     - Returns `ConcurrenceEvaluationResult` dictionary.
   - Guard endpoint `PATCH /api/work-orders/{order_id}/status`:
     - If requested status is `"resolved"` or `"verified_closed"`, verify that `cluster.verification_status == "REPAIR_VERIFIED"` or `cluster.concurrence_passes_count >= 3`.
     - If not verified, raise `HTTPException(status_code=400, detail="Cannot close work order: Multi-pass concurrence validation requires minimum 3 independent bus passes with |gz - 1.0| < 0.15g before authorizing payment clearance.")` unless overridden by administrative bypass with audit note.

3. Implement `backend/tests/test_concurrence_gating.py`:
   - `test_distinct_bus_diversity_rule`: Feed 3 passes all having `bus_id="BUS-01"`. Assert distinct bus count is 1, status remains `AWAITING_CONCURRENCE`, and `invoice_clearance_authorized` is `False`.
   - `test_three_pass_concurrence_pass`: Feed 3 passes from `BUS-01`, `BUS-02`, and `BUS-03` with $g_z \in \{0.98, 1.02, 0.95\}$ and `SMOOTH_SURFACE`. Assert distinct bus count is 3, status is `REPAIR_VERIFIED`, and `invoice_clearance_authorized` is `True`.
   - `test_vertical_gz_tolerance_band`: Pass with $g_z = 1.12g$ approved; pass with $g_z = 1.25g$ rejected as non-smooth ($|g_z - 1.0| = 0.25g \ge 0.15g$).
   - `test_recurrent_shock_triggers_fail`: Pass with $g_z = 1.45g$ ($|g_z - 1.0| = 0.45g \ge 0.35g$) triggers immediate `REPAIR_FAILED_RECURRENCE`.
   - `test_verify_concurrence_endpoint`: HTTP POST `/api/work-orders/{order_id}/verify-concurrence` returns 200 with complete validation schema.
   - `test_payment_clearance_lock`: Attempting `PATCH /api/work-orders/{order_id}/status` to `resolved` without 3 passes returns HTTP 400 error.
</action>
