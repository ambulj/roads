# Plan 01-02: PostGIS Spatial Clustering & High-Concurrency Telemetry Ingestion

<planning_context>
### Objective
Implement sub-50ms spatial clustering and high-throughput viewport queries (SCALE-02) alongside a bounded, high-concurrency telemetry batch flusher capable of absorbing 500+ transit buses streaming 5Hz telematics (up to 2,500 msg/sec) without connection pool exhaustion or table lock deadlock (SCALE-03). Multi-bus defect aggregation leverages native PostGIS `ST_ClusterDBSCAN` with Python DBSCAN fallback for SQLite, while the ingestion pipeline decouples instant WebSocket broadcasts from asynchronous bulk database transactions with prioritized queue backpressure.

### Scope Boundaries
- **In Scope:**
  - Viewport bounding-box filtering on `/api/v1/clusters?bbox=min_lon,min_lat,max_lon,max_lat` using PostGIS `geom && ST_MakeEnvelope(...)` on PostgreSQL and `between` bounds on SQLite.
  - Multi-bus defect clustering service supporting native PostGIS `ST_ClusterDBSCAN(geom, eps := 0.00005, minpoints := 2)` with scikit-learn/Python fallback on SQLite.
  - Decoupled `TelemetryBatchBuffer` in `backend/app/services/telemetry_buffer.py` with `asyncio.Queue(maxsize=10000)`, batch thresholds (500 records or 1.0s interval), and prioritized shedding (preserving defects and IMU shock alerts while dropping intermediate routine GPS pings during lock contention).
  - Integration of batch buffer into FastAPI application `lifespan` in `backend/app/main.py` with graceful shutdown flushing.
  - Non-blocking ingestion endpoint updates in `backend/app/api/endpoints/telemetry.py` pushing to WebSocket broker immediately and enqueueing for bulk insertion.
  - Verification test suites in `backend/tests/test_spatial.py` (viewport & clustering tests) and `backend/tests/test_ingestion_queue.py` (concurrency stress & backpressure priority).
- **Out of Scope:**
  - Native Rockchip RK3588 NPU C++ zero-copy inference pipeline (Phase 2).
  - IRC:SP:20 Clause 14 contractor financial debit ledger (Phase 3).
  - MapLibre WebGL UI components (Phase 4).

### Threat Model
- **T-01-03: Spatial Query Denial of Service (SQL Injection & Huge Bounding Boxes)**: Arbitrary or malicious `bbox` strings could trigger SQL injection or cause full-table sequential scans if unvalidated. Viewport queries must validate float coordinate ranges (`-180 <= lon <= 180`, `-90 <= lat <= 90`, `min <= max`) and clamp result limits (default 500, max 2000).
- **T-01-04: Ingestion Queue Memory Exhaustion (OOM & Data Loss)**: Unbounded queues under database lock stalls can consume gigabytes of RAM and trigger OS process killing. Mitigated by strict `maxsize=10000` queue bounding, 80% watermark prioritized shedding of non-critical GPS coordinates, and zero dropping of high-confidence defects (`confidence > 0.8` or `defect_type != 'NONE'`).
</planning_context>

### Task 1: PostGIS ST_ClusterDBSCAN & Bounding-Box Viewport Filtering
<name>Spatial DBSCAN Clustering & Viewport Filtering</name>
<read_first>

- .planning/phases/ROAD-01-enterprise-scalability-spatial-engine/01-RESEARCH.md (Section 3: Spatial Queries & Clustering)
- backend/app/api/endpoints/clusters.py (Existing cluster endpoints)
- backend/app/services/clustering_service.py (Existing clustering service)
</read_first>
<action>
1. Enhance `backend/app/services/clustering_service.py`:
   - Implement dual-mode multi-pass clustering:
     - On PostgreSQL: Run native `ST_ClusterDBSCAN(geom, eps := 0.00005, minpoints := 2)` over raw ingests partitioned by defect type, aggregating centroids using `AVG(lat)` and `AVG(lng)` or `ST_Centroid(ST_Collect(geom))`.
     - On SQLite: Fall back to Python density clustering (using scikit-learn or `app/spatial/dbscan.py` with Haversine distance metric equivalent to ~5.5m), grouping points with >= 2 passes.
   - Implement 15-meter road corridor snapping logic using `ST_DWithin(road.geom::geography, defect.geom::geography, 15.0)` on PostgreSQL and Haversine distance projection on SQLite.
2. Update `backend/app/api/endpoints/clusters.py`:
   - Add optional `bbox: Optional[str] = None` query parameter to `list_clusters` (`min_lon,min_lat,max_lon,max_lat`).
   - Validate and parse bounding box floats with boundary validation:
     - Ensure `-180 <= min_lon <= max_lon <= 180` and `-90 <= min_lat <= max_lat <= 90`.
   - On PostgreSQL: Query with `geom && ST_MakeEnvelope(min_lon, min_lat, max_lon, max_lat, 4326)`.
   - On SQLite: Query with `lat.between(min_lat, max_lat) & lng.between(min_lon, max_lon)`.
   - Apply result pagination/limit (default 500).
3. Expand `backend/tests/test_spatial.py` with integration test cases:
   - `test_viewport_query_fallback`: Insert sample clusters inside and outside Chennai bounding box `[80.14, 12.95, 80.25, 13.05]`. Query endpoint with bbox and assert only enclosed clusters are returned.
   - `test_dbscan_clustering_consistency`: Run clustering service with 3 points (Points A and B within 8m, Point C 500m away). Verify Points A and B merge into 1 cluster with `pass_count == 2`, while Point C remains separate.
</action>
<acceptance_criteria>
- `/api/v1/clusters?bbox=...` returns correct filtered points on SQLite and PostGIS.
- Invalid or malformed bounding boxes return HTTP 400 with descriptive error messages.
- Clustering correctly identifies multi-pass detections within ~5-15 meter radius.
- `backend/tests/test_spatial.py` passes all spatial compilation and viewport/clustering tests.
</acceptance_criteria>

### Task 2: High-Concurrency Telemetry Batch Buffer with Prioritized Shedding
<name>Telemetry Batch Buffer & High-Concurrency Ingestion</name>
<read_first>
- .planning/phases/ROAD-01-enterprise-scalability-spatial-engine/01-CONTEXT.md (Decisions D-13 through D-16)
- .planning/phases/ROAD-01-enterprise-scalability-spatial-engine/01-RESEARCH.md (Section 4: High-Concurrency Ingestion)
- backend/app/main.py (Application lifespan events)
- backend/app/api/endpoints/telemetry.py (Telemetry ingestion endpoints)
</read_first>
<action>
1. Create `backend/app/services/telemetry_buffer.py`:
   - Implement `TelemetryBatchBuffer` class:
     - Internal `asyncio.Queue(maxsize=10000)`.
     - Configuration constants: `BATCH_SIZE = 500`, `FLUSH_INTERVAL = 1.0` seconds, `HIGH_WATERMARK = 8000`.
     - `async def enqueue(self, item: dict) -> bool`:
       - If queue size exceeds `HIGH_WATERMARK`, inspect item priority.
       - If `item.get("defect_type") in (None, "NONE")` and `item.get("vertical_g_force", 1.0) < 1.3`: drop packet and increment `dropped_pings_count` metric.
       - Else: enqueue item (priority items are never dropped unless hard queue limit 10,000 is reached).
     - `async def flush_worker(self)`:
       - Runs continuously during application lifespan.
       - Gathers batches up to 500 items or flushes after 1.0 second timeout.
       - Uses `AsyncSessionLocal` to execute bulk inserts into `DBRawIngest` and `DBAuditLog`.
     - `async def start(self)` and `async def stop(self)`: Gracefully drains pending queue before termination.
   - Provide singleton instance `telemetry_buffer`.
2. Update `backend/app/main.py`:
   - In `lifespan(app: FastAPI)`:
     - Start `telemetry_buffer.start()` task.
     - On shutdown, `await telemetry_buffer.stop()` ensuring zero data loss during application restarts.
3. Update `backend/app/api/endpoints/telemetry.py`:
   - In `POST /api/v1/telemetry/ingest` and related ingestion handlers:
     - Immediately invoke `websockets.manager.broadcast()` with live coordinates for 60 FPS WebGIS updates.
     - Enqueue record into `telemetry_buffer.enqueue(data)` without awaiting database I/O transactions.
     - Return HTTP 200/202 instantly (< 15ms response latency).
4. Create `backend/tests/test_ingestion_queue.py`:
   - `test_flusher_triggers_on_count_threshold`: Enqueue 500 records and verify worker flushes batch immediately.
   - `test_flusher_triggers_on_time_threshold`: Enqueue 10 records and verify worker flushes after 1.0s interval.
   - `test_bounded_queue_backpressure_priority`: Flood queue beyond watermark. Verify 100% of defect detections (`defect_type != 'NONE'`) are retained while routine GPS pings are dropped.
   - `test_high_concurrency_stress`: Launch 50 concurrent `asyncio` tasks each submitting 50 telemetry packets (2,500 total) mimicking 500 buses at 5Hz. Assert all packets are persisted without deadlock or connection pool errors.
</action>
<acceptance_criteria>
- `TelemetryBatchBuffer` handles bursts up to 2,500 msg/sec without database lock errors.
- Intermediate GPS pings are dropped during extreme contention, while 100% of defect detections and vertical shocks are persisted.
- Endpoint responses complete in <15ms while WebSockets receive instant broadcasts.
- All tests in `backend/tests/test_ingestion_queue.py` pass.
- Entire backend test suite passes: `python -m pytest -o pythonpath=backend backend/tests/ -q`.
</acceptance_criteria>
